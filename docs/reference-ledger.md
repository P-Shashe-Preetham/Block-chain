# Reference Utilization Ledger

> This ledger operationalizes the final-project requirement to use every supplied source to the fullest. Maximum value does not mean maximum dependency count: each source must influence an implementation, specification, test, training artifact, operational control, or explicit non-adoption decision.

| Field | Meaning |
|---|---|
| Consulted revision/date | **Pending owner-led source review** until an exact upstream commit and date are recorded; no historical consultation is fabricated. |
| Decision | `current-runtime`, `runtime-candidate`, `project-pattern`, `comparison`, `future-gated`, `reference-only`, or `research-only`. |
| Evidence | The gate that must be linked before deeper adoption or a maturity claim. |
| Maintenance | Every adopted source requires an owner, update policy, license/provenance review, and sunset/revalidation condition. |

## Adoption rules

1. Only OpenZeppelin is currently a runtime dependency from the original 15 repositories. All other sources remain visible as curated inputs until a focused ADR, license/provenance review, security review, tests, and third-party notice update approve deeper adoption.
2. Sources with known or suspected restrictive terms require explicit legal review before distribution or hosted use. The project must not silently convert a reference into a runtime service.
3. Agent, scraper, design, and research sources may inform process or design but cannot receive production signing, key-release, authorization, deployment, merge, or privacy authority.
4. Situational sources are activated only when a measured requirement appears. Each activation must include a benchmark, failure test, threat-model update, license review, and removal path.
5. Exact stars, pricing, license status, upstream commit, and security status must be revalidated at the time of adoption; attachment-era descriptions are not permanent evidence.
